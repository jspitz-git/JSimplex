# F14 — Automatic pricing and weight recovery

Status: complete correctness verification and preset measurements passed. Parent: `cb56cbd` (F13).

## Behavior

The new explicit option `pricing=:auto` starts with steepest edge. Selected
primal and dual weights are checked against the already computed FTRAN/BTRAN
result. The check adds no basis solve per candidate. Primal floating weights
store square roots, so their comparison uses the corresponding squared ratio.
A discrepancy exceeding a factor of two, or nonpositive/nonfinite stored
weights, selects Devex with a fresh reference framework.

Under the adaptive strategy, completed stagnation windows can temporarily
select Dantzig. A return to Devex requires a two-window cooldown and a valid
weight reset for the current basis. Decisions use completed work and weight
quality, without wall-clock thresholds. The internal `adaptive_pricing=false`
ablation disables progress-based switches but retains numerical recovery.
Legacy strategy also permits explicit auto pricing with numerical recovery.
Existing explicit pricing choices retain their documented safety fallbacks.

Pricing history is owned by each workspace and copied for transactional pivot
and recovery trials. Failed trials cannot publish a mode/reset counter. Weight
rejections count attempted work. Phase changes reset history; recovery retains
its cooldown. An ordinary refactorization preserves valid steepest-edge caches
because the basis is unchanged; subsequent selected-weight checks use the
fresh factorization. Devex refactorizations rebuild their reference framework.

Automatic dual scores use exponent-scaled floating comparisons and widened
rational arithmetic to prevent overflow/underflow before a candidate can be
validated. Exact selected dual norms are accumulated in Rational{BigInt}.
Explicit pricing arithmetic remains unchanged. BigFloat weight comparisons
respect stored precision. User feasibility tolerances are unchanged.

## Preset measurements

The protocol was fixed before corpus outcomes. Three arms use the same F14
source and adaptive strategy: explicit steepest edge, auto with progress
switching disabled, and auto with progress switching enabled. All other
features remain enabled; clock-based refactorization is disabled. Each solve
uses Float64, PFI, native refactorization, 100000 iterations, 60 seconds, and
24576 MiB requested memory. Workers perform one uninstrumented warmup and, for diagnostic samples,
one additional instrumented warmup. MIPLib inputs
are explicit LP relaxations; the default 64-step stagnation window is unchanged.

NetLib adlittle and MIPLib pk1 each receive seven diagnostic-free samples per
method and arm. NetLib degen2 and the generated primal-chain130 each receive
one diagnostic/kernel-timed sample per method and arm; the chain has presolve
disabled. This gives 96 fresh observations in twelve groups. No parent raw
measurements are reused. The chain is mechanism calibration, not an independent
holdout. Pricing kernel costs must be interpreted together with iteration and
refactorization counts, switches, resets, rejected weights, and original-model
checks. Unavailable or inconclusive dual diagnostics remain visible.

No runtime, medium, or oversized full solves are included in this feature's
preset measurements. Future runtime runs retain 360 seconds per solve and the
24576 MiB memory request.

## Interpretation and limits

All 96 fresh observations returned OPTIMAL and passed original-model primal
feasibility checks. Optimal objective values agree across arms and methods:
adlittle 225494.9631623803, pk1 0, degen2 -1435.178, and the chain -1.
The raw artifact is [F14-results.json](F14-results.json).

The explicit degen2 paths retain F13's work counts: primal 1105 iterations and
599 refactorizations; dual 982 and 119. Automatic weight recovery changes these
to 1117/588 and 759/74, respectively. The two auto arms have identical paths
and events here; no completed stagnation window triggers Dantzig. The primal
performs one weight rejection/Devex switch, and the dual performs four.
Diagnostic time improves for dual but worsens for primal. Pricing-kernel time
also increases for primal. These are single diagnostic observations, so they
do not establish a general speedup. The seven-sample small-model timings show
no consistent advantage; pk1's work counts are unchanged. No new solved
coverage is demonstrated by this selection.

On the generated chain, each adaptive-auto method makes one Dantzig switch;
auto without progress switching makes none. All arms use 130 iterations with
six primal or seven dual refactorizations. The default-window chain ends
before the two-window return cooldown expires; the shorter-window targeted
regressions independently verify the return to a fresh Devex framework.

Nine observations expose mapped original-model dual witnesses. The six chain
observations have zero dual-sign and complementarity errors. All three degen2
dual observations retain a strict infinite complementarity diagnostic, caused
by a tiny wrong-sign multiplier on an unbounded side: 2.955113931335518e-13 for
explicit pricing, and 8.79296635503124e-14 for each auto arm. These raw values
are preserved and are not an independent complementarity certificate. The
remaining 87 observations explicitly report unavailable mapped witnesses.
Public Solution does not expose a dual witness; primal certification alone
must not be read as independent full KKT validation.

Automatic pricing remains an explicit choice. The observed mixed performance
supports further staged work and broader final validation before changing
any default.
