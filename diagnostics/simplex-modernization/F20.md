# F20 — Guarded crash bases

## Implementation

The internal `crash=true` policy constructs a candidate start in an independent
workspace. Both public strategies keep crash disabled by default. Structural
columns are ordered by their actual nonzero count and original index. Fixed and
zero columns are skipped. For each column, at most `max_pivot_candidates` of the
strongest eligible rows are scored for predicted primal-violation reduction.
This bounds candidate scoring rather than searching every row pair.

An exchange must reduce violation, keep the entering value within its bounds,
pass a relative pivot threshold, and pass independent FTRAN/BTRAN pivot
validation. Estimated and actual factor storage are bounded against the slack
factor (default multiplier 8). Periodic fresh factorizations bound the update
chain. Acceptance always requires a final fresh factorization, finite state,
reliable recomputed solves, and no increase in measured primal violation.

Nonbasic states use the objective and available bounds, including free,
upper-only, and fixed variables. The input model is unchanged. Returned bases
and workspaces own their state. `initialize_from_basis` validates the supplied
structure and bound states and verifies a fresh factor; it does not promise
primal or dual feasibility.

Until F21 generalizes artificial construction, the primal driver accepts a
structural crash start only if it is primal feasible. Otherwise it returns to
the independent slack workspace and uses the existing Phase I. The dual driver
uses measured feasibility through its existing startup logic. Discarded crash
pivots and factorization attempts remain consumed work. The original deadline
is shared, and a latched interruption returns `TIME_LIMIT` rather than starting
a new solve.

Stored BigFloat precision is honored for the initial slack fallback as well as
candidate construction. Exact arithmetic never converts to floating point;
checked arithmetic overflow during the candidate attempt returns the slack
fallback. Caller stop/logger exceptions retain their identity, and diagnostic
observer failures retain their wrapped cause.

## Measurement protocol

The `phase_one` suite compares crash off/on on the same implementation, with
presolve disabled, adaptive strategy, automatic pricing, PFI/native factors,
and timing-based refactorization disabled. MIPLib inputs are explicit LP
relaxations. Each algorithm receives two full warmup solves and three recorded
samples. Each solve has a 60-second limit and 100,000 completed-step limit;
workers request 24 GiB, clipped to reported physical memory.

Diagnostics separate the crash kernel time, observed phase time, phase iteration
counts, and total solve time. Phase times include work between phase events,
including phase construction before the following event. Crash kernel timing is
the narrower measure of crash construction itself. Phase step accounting uses
published pivot/flip events and global retry offsets; speculative refactorization
events do not count rejected candidate steps. Algorithm switches inside the same
auxiliary model with unchanged objective remain attributed to Phase I; changing
back to the original objective or a different model ends that attribution. A
small generated model reproduced the former misclassification (two Phase-I
steps reported under `phase_primal`) before this was corrected. All timings include enabled
diagnostics; observer overhead is reported separately.

No `runtime.mps`, `medium.mps`, or excluded oversized full solve is part of this
feature's phase-I comparison. Earlier F19 long-run results remain unchanged.

## Results

All 36 recorded solves returned `OPTIMAL`, passed the original-primal certificate,
and matched the GLPK 5.0 LP-relaxation objective within the recorded comparison
tolerance. The GLPK constraint/bound reader is independent; objective sense and
constant use the existing native-semantics adapter. Decompressed hashes match
between the external inputs and the reference fixtures. Maximum measured primal
error was `3.907985046680551e-12`; maximum original-objective evaluation error was
`1.658975179452682e-10` (256-bit error evaluation).

All primal crash attempts fell back to the slack start. Therefore the seven
fewer Phase-I steps on `flugpl` are **not evidence of reusing a crash basis**.
Consumed crash work is retained, so subsequent counter-dependent decisions can
change: for example, incremental primal audits run every 20 completed steps.
The subsequent path differs, while total steps increase from 23 to 24. The dual
method accepted the two structural MIPLib starts; the generated case made no
crash exchanges and accepted an unchanged slack structure.

These are small-instance observations with only three samples. The first primal

## Reproduction

Use the offline depot setup from the
[main plan](../../docs/superpowers/plans/2026-09-22-simplex-modernization.md).
The full verification commands were:

```sh
julia --startup-file=no --project=. -e 'using Pkg; Pkg.test()'
julia --startup-file=no --project=dev dev/tests/runtests.jl
```

For each ablation, use a policy file containing `refactor_timing = false` and
`crash = false` or `crash = true`, respectively:

```sh
julia --startup-file=no --project=dev dev/simplex_benchmarks.jl \
  --source=. --suite=phase_one --algorithm=both --simplex-strategy=adaptive \
  --pricing=auto --basis-update=pfi --presolve=off --iteration-limit=100000 \
  --samples=3 --time-limit=60 --memory-limit-mib=24576 \
  --diagnostics=on --kernel-timing=on --policy=POLICY.toml --output=RESULTS.toml
```
