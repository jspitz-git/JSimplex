## Implementation

Numerical failures can recover from the most recent compatible verified basis,
with the current basis as a bounded fallback. Float32 first uses Float64; other
floating transitions use BigFloat at 128, 256 and 512 bits. Explicit ceilings
above 512 allow further powers of two. Stored BigFloat precision is never reduced.
Exact rational models never enter floating recovery.

The new workspace has an actual factorization at the selected precision. The
entire simplex run uses that precision, including reduced costs, FTRAN/BTRAN,
ratio tests and basis updates. Typed boundaries separate Float32/Float64 and
BigFloat workspaces. Existing cheaper recovery runs before escalation; enabling
boosting alone does not change the initial crash or phase-I policy.

Original costs and bounds are restored before transfer and certification.
Initialization, legacy dual, both primal phase-I paths and original-model cleanup
retain an original-dimension workspace when numerical initialization fails.
Numerical failures at a working level can try the next permitted precision;
caller and observer exceptions retain their identity or observer provenance.

The result remains `DualRunResult{T}` and public `Solution{T}`. Primal values and
the independently obtained dual witness are converted to the original scalar type
and certified against the original stored model with the original tolerances.
An apparently optimal higher-precision point is rejected if original-type rounding
fails certification. Basic stationarity and actual-bound complementarity checks
remain mandatory. Finite products that overflow before exact cancellation can use
the existing Rational{BigInt} primal-feasibility fallback without relaxing the
absolute tolerance.

All levels share the original deadline and completed-step budget. Conversion and
failed factor attempts contribute to cumulative refactorization counts. A stop
requested by the final certification observer is honored before returning OPTIMAL.

## Memory scope

`max_precision_memory_bytes` defaults to 1 GiB and limits a conservative estimate
of the next transfer and factor allocation. The estimate accounts for independent
model/scratch storage, BigFloat limbs and multiple dense factor buffers. Markowitz
can form a dense Schur core and is therefore included in the dense estimate.
A rejected transfer returns an explicit numerical failure before allocating it.
This estimate is not a hard whole-process RSS limit. External benchmarks separately
enforce the 24 GiB address-space ceiling, clipped to available host/cgroup memory.

## Validation design

The binary ill-conditioned replay is checked with a dense Rational{BigInt} oracle.
It rejects the Float64 certificate, rejects the original-type rounded result after
128-bit work, and succeeds after 256-bit work. Further tests exercise real pivots
under all four basis-update methods and both factorization backends, Float32 to
Float64, stored 512-bit input under a 64-bit ambient context, precision ceilings,
zero and positive insufficient memory allowances, owned perturbations, callback
provenance, phase-I recovery and deadlines. CLI tests distinguish input precision
from actual working levels and preserve wider BigFloat diagnostic witnesses.

Before the finite-range guard correction, the targeted behavior gate passed
108/108 checks and the complete development suite passed 1,113/1,113 checks. Complete JET passed 225/225 with the
explicit cold-boundary contract described below. The final complete production and development gates passed as recorded above.
Frozen external comparisons and their source/input/policy audits are complete.
The comparisons retain all statuses and use seven samples for small cases and
three for runtime.mps, with two complete warmups. Runtime receives 360 seconds per
solve, including each warmup. MIPLib cases are explicit LP relaxations. Stress-only

matching their frozen compressed/decompressed SHA-256 values. GLPK independently
imports constraints and bounds; the existing reference adapter preserves the
native reader's selected objective, sense and constant. Every MIPLib solve is

GLPK reports OPTIMAL for `share2b`, `air03`, `10teams`, `runtime` and the

x=y=1, with objective x+2*y=3. The frozen manifest and both Rational{BigInt}
generated-fixture tests already specify 3. The artifact uses this exact analytic
reference and preserves the entire conflicting GLPK attempt in `glpk_attempt`.
An independent Fraction parse of the unchanged fixture confirms the equations,
coefficients, hash and objective. No solver code, input or tolerance was changed
to resolve this reference mismatch.

`blend` retains the previously documented rejection of its extended NAME header;
neither the reader nor the input was changed. GLPK returned its time-limit code 9
on `test.mps` after the 360-second solve budget, without proving an optimum. That
case has no reference objective. Reference jobs ran as correctness checks alongside
the complete suites and provide no timing comparison or performance claim.

## Opt-in benchmark configuration

Precision recovery is an internal numerical-policy capability, not a new
`SolverOptions` keyword. A benchmark policy file can enable it explicitly:

```toml
precision_boosting = true
max_precision_bits = 512
max_precision_memory_bytes = 1073741824
refactor_timing = false
```

For example, with that content saved as `precision-policy.toml`:

```sh
julia --project=dev dev/simplex_benchmarks.jl \
  --file=/home/jspitz/mps/runtime.mps --algorithm=both \
  --simplex-strategy=adaptive --samples=3 --time-limit=360 \
  --memory-limit-mib=24576 --policy=precision-policy.toml \
  --output=/tmp/simplex-precision-runtime.toml
```

The worker records input precision separately from observed working levels.
Stored higher-precision dual witnesses retain their precision during independent
error evaluation. Diagnostics disabled means that working precision is explicitly
unavailable, rather than incorrectly claiming that no escalation happened.

## Cold-start regression and inference boundary

The first full development run failed its existing 60-second cold replay check:
a tiny restored LP returned TIME_LIMIT. The test deadline and expected OPTIMAL
status were kept unchanged. With the same worker and snapshot protocol, the F22
parent completed in 19.45 seconds; the first F23 source returned TIME_LIMIT after
141.75 seconds. These are diagnostic reproductions alongside correctness work,
not warmed performance measurements.

A direct profile placed 11,002 of 13,814 active samples in type inference. Merely
marking the precision driver non-inline, or retaining the old callback path,
did not fix the regression; both experiments were discarded. Automatic recovery
now crosses one explicit cold inference boundary and asserts `DualRunResult{T}`.
The otherwise identical replay completed OPTIMAL in 15.20 seconds. The ordinary
solve no longer infers the entire higher-precision graph before it is needed.

This boundary intentionally performs one dynamic call on numerical recovery.
It adds no abstract workspace fields and leaves higher-precision factorization,
pricing, ratio tests and updates concretely typed. Direct precision-kernel JET
checks remain strict. Caller-level checks accept only RuntimeDispatchReport at
this unique boundary Method, reject every other report, and separately check
that the public and internal return types remain concrete. The three scalar
caller tests also require exactly one such intentional report.

The superseded production run was stopped; its partial result is not counted as
a passing suite. The repeated complete development suite passed, including all 16 repair-snapshot
checks under the unchanged replay deadline. The subsequent production run found the finite-activity regression described
below; that run is not counted as a passing gate.

## Exact fallback retains finite original-type row activities

Complete production verification found three failures in the existing overflow-row
certificate test: a finite primal x=2 with coefficient 1e308 and an unbounded row
was accepted after exact fallback, although its activity exceeds the Float64
finite range. The prior numerical rejection is preserved. Neither the existing
expectations nor user tolerances changed. That run passed 252,851 checks and
failed three of 252,854 in 121m53.5s; the benchmark gate prevented any measurements.

Exact fallback now checks the final activity against the original scalar type's
finite range before checking row bounds. Intermediate overflowing products may
still cancel to a finite activity, which is necessary for the precision-recovery
entry cases. New Float32/Float64 tests cover both signs, an exact value just beyond
the endpoint that nearest rounding would hide, and exact cancellation to 3. They
failed 20 of 22 checks before the fix and passed 22/22 afterwards. Focused
integration then passed 78/78 checks, including the unchanged original test and
both public initialization-overflow recovery paths. Both complete suites then passed on the corrected frozen source before any
external measurements started.

## Interpretation and retained limitations

All external samples remained at 53 working bits: these cases did not trigger
precision escalation. Their unchanged status coverage is evidence against an
observed loss of solvability in this corpus, not evidence of an external
higher-precision speedup. The independent binary basis replay demonstrates
the intended numerical recovery. The tiny generated primal case has a 1.29
boost-on/off median ratio (94.8 versus 73.5 microseconds); this overhead is
retained rather than hidden. No default is changed on this evidence.

The strict complementarity diagnostic for share2b reports infinity with both
policies. Its definition assigns infinity to a nonzero price pointing toward
an absent bound, even when the original dual sign error is below 5.5e-14.
The solver certificate separately applies the unchanged requested stationarity
tolerance. These raw infinite diagnostics are preserved; they are not counted
as finite independent complementarity checks or replaced by zeros. All
OPTIMAL outputs pass original primal certification and their accepted objective
references. Unfinished solves have no fabricated dual-error measurements.

A Windows BSOD interrupted the first boost-enabled holdout attempt. The local
Windows event recorded 0x18B (SECURE_KERNEL_ERROR); its underlying cause was
not established and is not attributed to solver failure or memory exhaustion.
The five completed groups, complete correctness logs and exact source hash
survived. The interrupted temporary holdout records did not. Only that group
was rerun after restoring the unchanged development environment, with fresh
warmups, identical numerical limits and persistent output storage. No missing
samples were reconstructed. Cross-reboot holdout speed ratios are excluded.
