## Numerical graph and source boundary

From `(L*U+F)*x[Q] == (B*x)[P]./Rs`, entering RHS nonzero original rows seed via P and FTRAN follows coupling column block to earlier row block. The leaving basis-position unit RHS seeds via Q and BTRAN follows the reverse direction. This distinction is implemented and independently checked. Exact-zero F slots do not propagate reach; duplicates are retained. Slot visits still count explicit-zero and duplicate slots, so discovery cost is not understated by silently compressing edges.

Exported L contains its n unit diagonal entries, while native one-RHS L kernels omit that implicit diagonal. Native-source/klu.c:224, 332, 465 and 618 show unconditional offdiagonal slot loops; U kernels also divide every diagonal. Consequently **L_stored + U_stored - n** counts the model's offdiagonal coefficient visits plus U diagonal divisions. The ordinary block model adds all F column slots of reached column blocks. The stronger BTRAN model charges reverse-incident slots instead, requiring a reverse incidence structure. This is a source-informed model, not proof of an installed compiled instruction count, an equal-cost flop model, or an implemented elision kernel. REPORT.md retains those distinctions.

The practical boundary is supported by the bound current source. Ordinary PFI calls the full base forward solve at src/factorization.jl:202 and applies eta history afterward. The ordinary triangular wrapper calls it at src/triangular_factorization.jl:769 and applies row updates/upper solve afterward. Alias and generic-vector wrappers may copy/convert RHS storage but do not mathematically transform its support first. The base operator is replaced at refactorization (src/factorization.jl:434 and src/triangular_factorization.jl:1242); update history does not demand a new BTF of that unchanged base. Fixed-base entering-support scenarios therefore test a useful input boundary for a possible full-KLU backend, while retaining all post-base update work.

Transpose source has the opposite boundary: PFI applies reversed transposed eta history before src/factorization.jl:248; triangular wrappers prepare/permutate RHS and solve the upper transpose before `_finish_triangular_transpose!`, which applies transposed row updates before src/triangular_factorization.jl:798. An outer unit RHS need not be unit or sparse there. The report correctly excludes that unsupported inference and also excludes private DirectLowerBackend, alternate hypersparse/controller paths, callbacks and uncaptured auxiliary/cost/certification RHS. No general precision or path coverage is inferred from this Float64 diagnostic.

Change classification is appropriately conditional. Exact changed entries below the old block diagonal can break the old upper partition; their absence preserves an upper partition but does not prevent an internal block split. Coupling-only changes preserve diagonal blocks only under fixed maps/scales. A changed absolute column contribution can change native row sums and numeric factors beyond the nominal block. Canonical minimum-column tokens compare column membership independently of block numbering, without claiming row ownership equivalence or counting every member of a changed group. Predictions have 161 exchanges per history; observed successor partition comparisons have 160. All reported counts agree with the raw witnesses.

## Computational work and retained memory

**No unnecessary new production work or retained-memory cost was introduced: there is no production-code change. No remaining material avoidable diagnostic work/memory cost was found for the approved evidence scope.** The bounded diagnostic deliberately pays for a fresh assembly, factorization, combined extraction, finite/permutation/structure checks, two B hashes, identity matvec actions, forward/reverse graph construction, two reach queries, column-difference sorting and witness conversion/write at every one of 483 states. The additional old-B structural scan is 483 O(nnz(B)) scans and justifies the old-upper-partition premise. Those scans and checks serve evidence or numerical safeguards; they are not proposed per-pivot production overhead. Input hashing and nine anchor comparisons have their separately limited frequencies. The original redundant slice copies were removed before launch; entered CSC slices already own their buffers.

Graph construction is O(n + blocks + Fslots); reverse construction retains duplicate slots. Reach traversal pays reached outgoing/incoming slots, but this diagnostic also allocates/initializes masks and queues and scans block weights for each query. Current forward/reverse CSR typed payload is exactly **16*(blocks+1) + 18*Fslots bytes** on the asserted 64-bit environment; original-row/column maps and dimension/LU weights add **16*n + 16*blocks bytes**. The independently reproduced median totals agree with the report's 2.196 MiB / 2.275 MiB / 28.85 KiB. These are typed payloads, not a complete resident or allocated-byte footprint. Native factors, owned L/U/F exports, headers/capacity, queue/stamps, hash and witness conversion buffers remain additional costs. Forward-only candidates may omit reverse incidence. Exported factors alongside native factors can duplicate numeric storage.

Factors and exports are local to profile; result records retain scalar/string dictionaries and one previous column-token vector, with explicit GC every eight states and one captured history live at a time. This bounds intended retention but does not establish native-free completion. The 5M factor-slot guard is checked after allocation, so it is not a preallocation memory guarantee; the unchanged process VM/RAM/swap guard remains relevant. Total witness output is below the 512 MiB limit. The offline fixed-base pass retains only nine graphs plus 161 entering supports for the current history and scalar output rows, rather than all 161 factor exports.

The reported opportunity is correctly weighted: current-basis runtime FTRAN median modeled work remaining is about 45.0%/57.7%; fixed-base scenarios remain about 42.2–58.3%. Fast0507 retains most work. BTRAN's few reached blocks include the expensive core, so ordinary block-only work remaining is about 83.0%/86.2% on runtime, not the roughly 19–21% block fraction. Reach discovery itself incurs the reported median F-slot passes (12,224/13,279 FTRAN; 14,369/16,556 BTRAN), before dense preparation/gather/reset, update-chain work, finite/residual checks and memory effects. None of these counts alone proves net savings. Future retained graph metadata requires ownership/invalidation and O(n+blocks+Fslots) storage budgeting; future whole-call comparisons must preserve safeguards and distinguish kernel work from numerical trajectories.

No before/after production timing benchmark is required for these isolated diagnostic/documentation additions. The 23.16-second process duration includes initialization/compilation/GC/I/O and is correctly not used to claim solve speed or allocation reduction. Actual graph-local arithmetic, signed-zero/exception behavior, support alias invalidation, non-Float64 behavior, sparse/dense representative whole-call timings and full-solver behavior remain untested. The final recommendation is appropriately an experiment to design and admit separately; overall block-local SS and production integration work remains open.
