## Performance decision and uncertainty

I independently recalculated every side median/MAD/range/sample series, paired ratio summary and six nested timing summaries from the saved windows; they match the audit. Six of eight cells fail median paired whole-time <=0.95. Native sparse32, dense32 and sparse96 increase median allocation events by five, nine and one. Sparse96/Markowitz has only one of seven faster pairs and a 1.047715736 paired median. Only sparse32/Markowitz passes all first-process conditions. Consequently first_process_viable is false, and there is only one cost run.

Candidate median bytes fall in all eight cells, but that does not offset the time/event failures. Every warm/measured final graph and all probe graphs pass the 1.10 cap; the largest observed probe graph ratio is 1.0196359268157458. This memory result also does not offset other failed gates.

All 112 measured compile/recompile times are zero. The 48 recorded warm windows also report zero compile/recompile, which does not establish zero compilation during imports or earlier untimed preflight/probe work. Four measured windows record GC: sparse96/native reference 16.413201 ms, dense96/native reference 5.315801 ms, dense96/Markowitz candidate 3.9486 ms, and dense96/Markowitz reference 3.956 ms. Those windows and every outlier remain in the statistics. Ratios span values as low as 0.01802092797 and as high as 4.1925801783. Short whole-lifecycle windows, seven pairs and a single process do not support a universal speedup/slowness or isolated-kernel attribution. The paired numerical trajectories agree and use the same eight-update schedule; fewer iterations are not being used as performance evidence.
