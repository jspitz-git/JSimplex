## Important I1 — distinguish logical live state from backing identity after reservation failure

The Task1 failure test requires “original live owners/values/order/handles” while permitting changed unused reserve. Read literally, this can require the original backing owners or row positions to survive. The inherited `_bgu_insert_at!` calls `_bgu_reserve_row!` before block reservation. A successful row reserve publishes a new row buffer and repairs reciprocal positions, and a later split/descriptor allocation can fail. Descriptor reserve can likewise replace all seven backing arrays before slab allocation fails. Requiring unchanged backing identities or reciprocal physical positions would contradict the inherited implementation and the intended nontransactional reserve contract, or invite unnecessary rollback/copies.

Specify that logical live values, row/column order, encoded handles, unique ownership and complete partition remain valid; completed row/descriptor reserve publication may replace backing identities and reciprocal row positions while preserving their consistency. The free-split helper itself changes no active extent/row handle. Distinguish this from earlier numerical edits in a failed update, which are already expressly permitted and require refactor before reuse. Apply the clarification consistently to the spec and Task1 test expectation. This is a bounded contract clarification; no new rollback mechanism is requested.

## Design and invariants

The chosen demand rounding occurs before capacity-bin selection. A free3 extent is correctly unavailable for a target4 request, while arbitrary imported tails and remainders remain reusable for suitable later targets. Exactly one positive suffix descriptor is sufficient; recursive splitting, coalescing and global scans are unnecessary. Donor identity and address remain stable. Reserve-then-take is implementable with one synchronous outstanding reservation and the existing insertion commit point.

Prechecking descriptor/handle limits, checked address arithmetic and local bounds before unlinking, reserving seven metadata arrays privately, and publishing only a complete partition cover the new mutation. A successful wholly free append followed by failed split reserve is safe under the stated reserve-publication allowance. Free clearing is inherited: deletion, merge, relocation and column clearing leave free cells zeroed. Splitting does not require extra coefficient copying or clearing. Initial import, row backrefs, active linked lists, free-bin links and unused descriptor slots are accounted for. The extent swap in occupied-block growth preserves encoded row handles even when the free donor ID becomes the old free extent.

The adapter can retain numerical operation order while traversing differently sized extents. Existing merge decisions may differ because capacities differ, so identical source loops alone do not prove identical bits; the planned independent bitwise/order/history comparisons, signed-zero and exception cases are necessary. The plan includes distinct entering/DSE provenance, nonidentity q, rotations, alias rejection, copy independence and atomic full-refactor publication. No safeguard, tolerance, precision or backend change is proposed.

## Computational work and memory verdict

**No unnecessary new production work or memory mechanism was found in this design.** No production code changes in this planning scope. The new work is target selection, bounded capacity-bin search and O(1) local descriptor/link writes per free request when reserve exists. Allocation growth, metadata copying/zeroing, slab initialization and relocation are separately charged. There is no new full scan, solve, conversion, invariant walk, mirror or retained reservation object in the solve/update loops. Existing per-RHS loops may nevertheless visit more active blocks because capacity-dependent merges change layout; unchanged loop text is not a speedup claim.

The ledger correctly retains `16C+4R+28K+32n+656` and outer pointers `8n+24D`, plus headers/backing reserve and the full factor graph. A free split saves no retained coefficient bytes by itself. It adds one initialized descriptor; a growth event allocates all seven arrays and copies their old prefixes. Append then split can trigger two separate growth events. The geometry of a slab partitioned into size4 extents adds56 initialized descriptors (1568 logical descriptor bytes), without claiming the actual K growth/header cost equals that number. Int32 encoding and `32*Knew` checks remain relevant even with spare descriptors.

The monotone-growth bound of31 old tuples copied holds for every starting exact tail1..31. It does not hold over arbitrary delete/merge/refill sequences; the plan correctly excludes that inference. Fine-grained metadata and repeated relocation can regress dense updates. Fragmented sub-target free space can force new slabs despite ample free capacity, so no live-proportional memory bound follows. Complete copy/refactor retained graphs and temporary old/new coexistence are required. Sparse and dense measured comparison, all intermediate checkpoints, aggregate bytes AND events, and operation counters remain required before any performance claim.
