## Computational work, allocations and retained memory

**No unnecessary computational work, allocation, or retained-memory defect was identified by this source review.** This is a bounded source judgment, not an allocation measurement or speedup claim.

At setup and every refactor the candidate performs one ordinary factorization, export, validation and packing. Validation is O(nnz(L)+nnz(U)+n), with one n-bit scratch reused for two permutations. Markowitz extraction scans the dense core twice and builds triplets/CSC; native extraction converts CSR L and may perform one native orientation solve plus matrix-vector checks and private work vectors (`src/huangfu_hall_factorization.jl:89–118,166–198,208–260`). Those costs are explicit and not zero-copy. No HH upper row-index is constructed for the direct consumer.

Normalization creates D and one nnz(U) values buffer, scans/divides once and copies only after complete validation (`direct-factor.jl:77–90`). The temporary preserves failure atomicity and avoids recomputing every division in a second validation/commit pass; it is a defensible work/memory tradeoff, not a leak. Packing copies each U row/value once into manager-owned storage; temporary CSC U and the ordinary backend/workspace are absent from the successful returned object graph (`direct-factor.jl:127–143`). Native deallocation timing and peak live memory remain unmeasured. Fallback alone retains its needed ordinary backend.

Each FTRAN/BTRAN adds lower substitution and O(n) scaling/permutation, optionally D scaling, with O(nnz(L)+n) work and owned n-length transpose scratch. There is no new per-solve full-factor validity scan, factorization, temporary array construction API, or history-length-dependent metadata cache in these lower kernels. Manager update-chain work and cache scans remain existing algorithms. Copies intentionally retain shared read-only lower arrays and live immutable history, while owning mutable upper/permutations/scratch (`direct-factor.jl:18–22`; production copying at `triangular_factorization.jl:1248–1280`).

Whole-manager transactional refactor reconstructs scratch/cache/history and gives up ordinary refactor workspace/upper-buffer reuse (`direct-factor.jl:154–160` versus ordinary `triangular_factorization.jl:1221–1245`). This is an explicit architectural cost in the frozen plan and preparation ledger, not a demonstrated efficiency improvement. It must be charged in both refactor windows in Task3. No benchmark is required or authorized for this offline stage. Compilation/initialization/ordinary iterations/refactor costs, sparse/dense representative cases, total bytes/events and retained memory remain unqualified until separately admitted measurements.
