## Work and memory budget

The current tuple factory requests20 zero values, temporary collection and conversion on each dimension decision, including rejected eligibility. The other two sites initialize a counted workspace and return no-count statistics. These are fixed-width O(20) operations independent of n, nnz(U) and update-chain length. Runtime allocation count is not generally guaranteed by that source count.

The proposal moves zero-tuple initialization to module setup and retains one fixed immutable20-Int value (160 scalar payload bytes on the pinned64-bit platform; total object/header/module retention is unmeasured). It adds no per-call vector/matrix scan, basis solve, conversion, cached factor or invalidation scheme, and does not copy/mutate BigFloat or Rational scalars. Mutable counters and their existing tuple-replacement updates remain unchanged. The benefit would be a small frequent overhead reduction and restoration of the intended cheap rejection contract, not a prediction of material end-to-end solver speedup. There is no production change in this analysis and no additional production work or memory.
